## 0. 总前提（建议对齐）

| 前提 | 含义 |
|------|------|
| 本地单机控制台 | 无账号体系、无云端同步密钥；威胁模型是**本机误提交 / 误拷贝 / 日志泄漏**，不是对抗 APT |
| 密钥继续文件 | 方向一已明确：`config/cookies.txt`、`config/llm.env` **不进 SQLite**；本方向**不推翻**该边界 |
| 脱敏已有底座 | 方向七 `log_redact` + 诊断包排除密钥文件已落地；本方向**复用并清单化**，不另起一套脱敏 |
| 路径策略已可用 | `dev` / `installed`（`%APPDATA%\Binggo`）/ `portable`（`BINGGO_PORTABLE=1`）+ `BINGGO_HOME` 覆盖已存在 |
| 无真实线上老用户 | 不做「加密格式迁移老用户」产品级兼容；若日后做加密，开发机可重登 / 重填 Key |
| 行为不改业务 | 登录、LLM 测试/保存、参与文案、扫码退出等**用户可感知行为不变**；只加强校验、约定与防护 |

## 1. 现状摘要（拍板依据）

### 1.1 已有能力

| 层 | 现状 | 路径 |
|----|------|------|
| Cookie | 明文 `cookies.txt`（UTF-8 单行）；扫码写入；可读 `BILI_COOKIE` 环境变量 | `src/app_paths.py`、`bilibili_login.py`、`bilibili_client.py` |
| LLM | 明文 `llm.env`；API 只回 `api_key_hint`；请求体有 Pydantic | `src/llm_config.py`、`llm_settings.py`、`web/schemas/settings.py` |
| 参与文案 | 已在 SQLite `user_settings`（方向一） | `src/user_settings.py` |
| 路径 | `USER_HOME` / `CONFIG_DIR` / `DATA_DIR`；`runtime_label()` | `src/app_paths.py` |
| Git | 忽略 `cookies.txt`、`llm.env`、`data/` 等 | `.gitignore` |
| 脱敏 | SESSDATA / bili_jct / LLM_API_KEY / Bearer / 长 token；诊断包不含密钥文件 | `src/log_redact.py`、`diagnostics.py` |
| Job | `sanitize_params` 丢弃 cookie/token/api_key 类键 | `src/job_store.py` |
| 前端 | LLM 密码框 + hint；无手动贴 Cookie 主 UI | `web/frontend/src/settings` |
| 打包 | spec 只打 `*.example`；便携说明指向 APPDATA / Portable | `packaging/windows/*` |

### 1.2 真实痛点

| 痛点 | 表现 |
|------|------|
| 明文落盘无约定 | Cookie / API Key 无权限硬化、无统一「敏感清单」；新人不知哪些路径绝对不能进 git / 诊断包 |
| 配置缺 schema | `llm.env` 手写解析；坏 URL / 空 Key / 脏行缺少统一校验与安全默认 |
| 路径认知分散 | README、打包说明、关于页不一致时，用户分不清「数据在哪、卸载删不删」 |
| 便携版易整夹拷走 | `BINGGO_PORTABLE=1` 时密钥与 exe 同树，同步盘/U 盘拷贝风险更高 |
| 启动无自检 | 不会提示「密钥文件过宽权限 / 误把 HOME 指到仓库外危险位置」等 |

### 1.3 路线图讨论清单对照

| 原问题 | 本文件处理 |
|--------|------------|
| 加密是否进 v1，还是先「检测明文 + 权限提示」？ | 议题 **A** |
| 便携版与安装版路径是否再简化？ | 议题 **E** |
| 日志/诊断包如何脱敏？ | **方向七已落地**；本方向只做清单对齐（议题 **F**） |

## 2. 拍板结论一览（已定）

| 编号 | 议题 | 结论 | 说明 |
|------|------|------|------|
| **A** | 密钥是否静态加密 | **A1** | 明文 + 硬化（不加密） |
| **B** | 配置校验形态 | **B2** | 加载/写入时 Pydantic 模型校验 |

| **E** | 路径策略 | **E1** | 保持现三模式，强化文档/关于页 |
| **F** | 敏感清单 | **F1** | 代码内单一 registry |
| **G** | HTTP 绑定 | **G1** | 钉死 loopback 意图并启动断言/文档 |
| **H** | 与方向七 | **H1** | 复用 `log_redact`；扩展清单而非重写 |
| **I** | Git / CI 防泄漏 | **I1** | ignore + 轻量「未跟踪敏感文件名」检查 |
| **J** | UI 改动幅度 | **J1** | 最小：概览展示数据目录与 runtime |

### 边角（已定）

| 编号 | 议题 | 结论 |
|------|------|------|
| **①** | Cookie / llm.env 路径 | **钉死**现有 `CONFIG_DIR` 文件名；不改名、不进库 |
| **②** | 环境变量旁路 | **保留** `BILI_COOKIE` / `LLM_*`；自检可提示覆盖 |
| **③** | `api_key_hint` | **保持**首尾掩码 |
| **④** | 卸载保留 | **保持**安装版数据在 `%APPDATA%\Binggo`、卸载不删 |

| **⑥** | 分期 | P1 清单+校验+权限+文档 → P2 自检/轻 UI → P3 CI 防泄漏 |

## 3. 议题展开

### 3.1 A — 静态加密

| 选项 | 内容 | 代价 |
|------|------|------|
| **A1（建议）** | 继续明文文件；权限尽力收紧；清单 + 自检 + 文档 | 本机能读文件的用户/恶意软件仍可读 |
| **A2** | Windows DPAPI 或 `keyring` 加密落盘 | 便携盘换机失效；备份/重装痛苦；开发调试变难；跨平台分叉 |
| **A3** | v1 只做「明文检测 + 提示」，加密明确留二期 | 与 A1 接近，少做一点硬化也算 A3 |

**建议 A1：** 本产品是 loopback 本地工具；方向七已挡住日志/诊断主泄漏面。加密对「防自己误 git 提交」帮助有限（防提交靠 ignore + CI），对便携模式反而有害。若未来要做 A2，也应**仅 installed 模式**可选，且不作为本方向验收。

### 3.2 B — 配置 schema

| 选项 | 内容 |
|------|------|
| **B1** | 只写文档与清单，解析逻辑不动 |
| **B2（建议）** | `llm.env` 读写经 Pydantic（或等价模型）校验 URL/必填/默认值；Cookie 做「存在性 + 关键字段是否可解析」校验（不把整段 Cookie 拆成强 schema 表） |
| **B3** | 全面 `pydantic-settings`，环境变量/文件/DB 合成一套 Settings 单例 |

**建议 B2：** 收益集中在 LLM 与启动失败可理解性；B3 改动面大、与「密钥继续文件、文案在 DB」的分裂存储冲突，不划算。

校验失败策略（建议）：

- **写入 API**（保存 LLM）：继续方向四统一错误体，`VALIDATION_ERROR`  
- **启动加载**：坏配置 → 日志警告 + 功能降级（如 LLM 未就绪），**不**阻止整个控制台启动（除非文件损坏到无法忽略且可选）

### 3.3 C — 文件权限

- 写入/更新 `cookies.txt`、`llm.env` 后：**尽力**设仅当前用户可读（POSIX `0o600`；Windows 用现成方式或跳过）  
- 失败只打警告，**不**导致登录/保存失败  
- 不引入必须管理员的操作

### 3.4 D — 启动自检（建议项）

软检查示例（实现时可裁剪）：

1. 敏感文件是否存在且权限过宽（能检则检）  
2. `USER_HOME` 是否落在明显危险同步目录（可选、可只文档提示）  
3. 是否正通过 `BILI_COOKIE` / 环境变量覆盖文件（提示，不禁止）  
4. `runtime_label` + 数据目录路径写入启动日志（已有部分可加强）

UI（建议轻量）：概览或关于区展示「数据目录 / 运行模式」；仅严重项用 toast/横幅，避免恐吓式安全中心。

### 3.5 E — 路径策略

**建议 E1 保持：**

| 模式 | `USER_HOME` |
|------|-------------|
| 开发 | 仓库根 |
| 安装包默认 | `%APPDATA%\Binggo` |
| 便携 | exe 同目录（`BINGGO_PORTABLE=1`） |
| 覆盖 | `BINGGO_HOME` |

本方向工作：README / 打包说明 / 控制台「关于或概览」三处**说法对齐**；便携说明中加一句「密钥与程序同目录，勿把整个文件夹同步到公开盘」。

### 3.6 F — 敏感清单（F1）

建议单一模块（名待定，如 `src/secrets_inventory.py`）列出：

| 类别 | 示例 |
|------|------|
| 文件路径 | `cookies.txt`、`llm.env` |
| 环境变量名 | `BILI_COOKIE`、`LLM_API_KEY`、… |
| 日志/字典键 | 与现 `log_redact` / `sanitize_params` 对齐 |
| 诊断排除 | 明确永不打进 bundle 的路径 |

`log_redact`、`diagnostics`、自检、文档生成**引用同一清单**，避免三处漂移。

### 3.7 G / H / I / J（短）

- **G1**：文档 + 启动确认监听 `127.0.0.1`（若已是则只加固断言/注释）；禁止把「改绑 0.0.0.0」写成推荐  
- **H1**：脱敏规则以方向七为准；本方向只补清单缺口  
- **I1**：例如测试断言「仓库不得 track `config/cookies.txt` / `config/llm.env`」或 CI `git ls-files` 检查  
- **J1**：不改 LLM 保存/测试、扫码登录主流程；最多加数据目录展示与自检提示

## 4. 拍板取舍摘要（建议选 vs 不选）

| 拍板 | 选 | 不选（及原因） |
|------|----|----------------|
| **A1** | 明文 + 硬化 | A2 伤便携与备份；收益不对齐威胁模型 |
| **B2** | 读写校验模型 | B3 大一统 Settings 过重 |
| **C1** | 尽力权限 | C3 强 ACL 脆、跨环境难测 |
| **D1** | 软自检 + 轻提示 | D2 硬失败影响「先打开再说」 |
| **E1** | 保持三模式 | E2 砍便携伤现有打包承诺 |
| **F1** | 单一清单 | F2 继续漂移 |
| **G1** | loopback 钉死意图 | G2 HTTPS 超范围 |
| **I1** | ignore + 轻检查 | 仅靠人工 |

## 5. 目标形态（建议落地后）

```text
                    ┌─ secrets_inventory（单一清单）
                    │
 app 启动 ──► 自检（软）──► 日志 / 可选轻 UI
                    │
 Cookie / LLM 读写 ──► 校验模型 ──► 明文文件（权限尽力 0o600）
                    │
 日志 / 诊断包 ──► log_redact + 清单排除（方向七）
                    │
 文档 / 关于页 ──► USER_HOME、runtime、卸载保留、便携风险说明
```

**仍不进库、不进诊断包：** `cookies.txt`、`llm.env`  
**仍可用环境变量：** 开发 / CI / 高级覆盖

## 6. 设计想法（背景，供对照）

### 6.1 为何做方向八

方向一把业务态收进 SQLite 后，**唯一仍明文躺在磁盘上的高价值秘密**就是 Cookie 与 LLM Key。方向七堵住了「日志和求助包」泄漏；方向八要堵住「约定不清、校验缺失、权限过宽、路径误解」——这是本地产品的配置治理，不是安全产品化。

### 6.2 为何建议不做 v1 加密

| 场景 | 加密痛点 |
|------|----------|
| 便携版拷到另一台 PC | DPAPI/用户凭据绑定，直接打不开 |
| 重装系统 / 新用户配置文件 | 密钥作废，只能重登 |
| 开发机多 `BINGGO_HOME` | 调试成本上升 |
| 防 git 误提交 | 加密解决不了「密文进库仍是事故」；应用 ignore + CI |

### 6.3 与「配置项增多」的关系

参与文案已在 DB；`sources.yaml` 仍是运维文件。本方向**不**把 `sources.yaml` 或 watch 名单升格为密钥；schema 重点落在 **LLM + Cookie 存在性 + 路径/清单**。

### 6.4 威胁模型（写清边界）

| 在范围内 | 不在范围内 |
|----------|------------|
| 误把 `config/` 提交到 git | 本机 root/管理员刻意读取用户目录 |
| 诊断包 / 日志带出 SESSDATA | 恶意扩展 / 键盘记录 |
| 便携目录被同步到公开网盘 | 远程攻击者打非 loopback 端口（部署错误另论，用 G1 防呆） |
| 坏 `llm.env` 导致难懂失败 | 多用户 ACL、企业 MDM |

### 6.5 与其它方向

| 方向 | 关系 |
|------|------|
| 1 | 密钥继续文件；不进 `binggo.db` |
| 4 | LLM/设置 API 错误体继续统一；可加强校验 |
| 7 | 脱敏与诊断排除对齐清单 |
| 9 | 文档与便携说明供打包页复用；本方向不做更新检查 |
| 10 | MCP 若暴露工具，危险操作仍 deny-by-default；密钥不经 MCP 回传 |

### 6.6 建议分期

| 期 | 内容 |
|----|------|
| **P1** | `secrets_inventory`；LLM/Cookie 校验；写文件后尽力权限；README/打包说明对齐 |
| **P2** | 启动自检；概览/关于展示数据目录与 runtime |
| **P3** | CI/测试防敏感文件名入库；补 pytest |

## 7. 验收红线（建议）

切换/实现完成后至少满足：

- [ ] 敏感路径/键名有**单一清单**；诊断包与 redact 引用一致  
- [ ] LLM 保存非法 URL / 明显坏配置 → 统一校验错误，不写烂文件  
- [ ] 登录保存 Cookie、LLM 保存 Key 后，权限尽力收紧（能检的平台可测）  
- [ ] 启动日志或关于/概览能看到 **数据目录 + runtime**  
- [ ] 登录 / LLM 测试保存 / 参与文案 / 退出登录行为与改前一致  
- [ ] **无**强制 DPAPI/keyring；**无**密钥进 SQLite；**无**云同步  
- [ ] `.gitignore` 仍忽略真实密钥文件；有轻量防 track 检查

## 8. 非目标

- 账号系统、云端保险箱、密钥托管  
- v1 强制静态加密（DPAPI / keyring）  
- 本地 HTTPS / 非 loopback 多机访问  
- 把 `sources.yaml`、监控名单、参与文案改造成「密钥」  
- 企业级审计、EDR、防屏幕窥探  
- 改变方向九的安装包技术选型（仅提供文档素材）
