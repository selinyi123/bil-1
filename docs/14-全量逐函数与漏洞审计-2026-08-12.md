1. 对所有项目自有 `.py` 通过 Python AST 枚举函数、方法和命名嵌套函数；对 `web/frontend/src` 通过 TypeScript 语法树枚举函数声明、函数表达式和箭头函数。

## 3. 已验证有效的承重机制

以下结论来自代码与相关测试，而非仅复述规格文档：

1. **身份单一来源**：`resolve_effective_uid` 的优先级与账号池切换逻辑一致；环境变量覆盖时拒绝切号，避免 UI 身份与请求 Cookie 分叉。
2. **参与结果的原子持久化**：`record_participation_outcome_unlocked` 在同一 `session_scope` 写入动作台账、参与状态和活动状态；测试覆盖异常回滚与动作裁剪。
3. **`dry_run` 贯穿**：参与预演不会发送写接口、不会写 participation 台账或把活动标为已参加；三连的内部失败与用户取消分开编码为 `business_partial` / `cancelled`。
4. **清理 exact ownership**：仅删除 `created_dynamic_id` 精确命中的 Binggo 转发，旧记录才兼容源动态 ID；白名单同时保护删动态和取关。
5. **schema fail-closed**：未来版本数据库在写入前拒绝，meta 丢失且业务表存在时拒绝启动；不会自动降级回写。
6. **本机控制面**：`dashboard_server` 固定 loopback；`LocalControlPlaneGuard` 对 `/api` Host 做 allowlist、对带 Origin 的 mutation 做 loopback Origin 校验。
7. **秘密回显防护**：Notify / LLM / Proxy / DS-10 的 GET/PUT 均有脱敏或占位符恢复链；前端不把 LLM/通知秘密写入 storage 或 console。
8. **实时通道抗压**：EventHub 对订阅数和队列有上限，SSE 用 `finally` 退订，避免慢订阅无限积压。

## 4. 缺陷与安全审计结果

### 4.1 P1：已确认，应优先修复

#### A-01：清理分区时边删边翻页，会跳过前移的关注用户

- **位置**：`src/clear_follows.py:323-334`，`clear_follows`。
- **状态**：已确认；纯内存 120 人 FakeClient 中，`cancel_attention` 实时收缩分区后，仅取关 70 人，残留 50 人。
- **根因**：第 1 页删除后元素前移，代码仍递增请求 `pn=2`，跳过已前移的条目。
- **影响**：任务可显示完成而临时关注分区仍残留；后续清理结果取决于分页和服务端更新时机。
- **修复**：真实执行时持续读取第 1 页直至空，或先快照所有 UID 再按快照取关；维护已处理 UID 以防死循环。
- **测试缺口**：`tests/test_line_clear.py` 有单页/静态分页/白名单/dry-run，但没有“删除导致分页收缩”。

#### A-02：DS-10 失败路径会把完整外部源 URL 写进错误和日志

- **位置**：`src/sources/ds10_api.py:109,113,140,145,149,259`，`_fetch_payload_with_meta` / `check_update`；脱敏器 `src/log_redact.py:23-29`。
- **状态**：已确认；含 query token 的 URL 经异常路径和现有 `redact_text` / `sanitize_log` 后仍保留 token。
- **根因**：异常字符串拼接原始 `source`；通用脱敏不删除普通 URL query、userinfo 或签名 path。
- **影响**：DS-10 访问凭据可进入 Job 日志、SQLite Job 结果、JSONL、诊断包和控制台。
- **修复**：异常只使用 source hash 或 `mask_external_source(source)`；日志脱敏增加 URL 级清理（userinfo/query/fragment，必要时 path 截断）；加入 query token、userinfo、signed URL 用例。

#### A-03：AutoScheduler 快速 stop → start 可保留两个并发调度循环

- **位置**：`web/auto_scheduler.py:140-155,160-172,310-334`，`start` / `stop` / `_loop`。
- **状态**：已确认；最小并发探针得到 `peak_concurrent_loops=2`。
- **根因**：`stop()` 只 `set()` 共享 Event、不等待旧线程退出；紧接的 `start()` `clear()` 同一 Event 并覆盖 `_thread`，旧循环恢复运行。
- **影响**：同一时间槽可能重复投递 refresh/triple，或者相互干扰停机状态。
- **修复**：每一代线程使用独立 stop Event，或 `stop()` join 旧线程后才允许 start；增加 generation token；补 start/stop/restart 竞态测试。

#### A-04：运行中 Job 的 Web mutation fail-closed 不完整

- **位置**：门禁只覆盖 `web/app.py:233-265` 的切/删账号和 `web/product_routes.py:52-57,129-200` 的 DS/代理；未门禁的 mutation 包括 `web/app.py:187-213,276-283,518-559,595-667` 的监控名单、ack、增强/通知、LLM、参与文案与 logout。
- **状态**：已确认，与根 `AGENTS.md` 的“Web mutation：Job 运行中 fail-closed”约束不一致。
- **影响**：运行中的参与任务可能读取到中途改变的文案/增强/通知；logout 可移除当前身份，造成单任务上下文漂移和不可回滚的部分副作用。
- **修复**：定义统一 mutation dependency/middleware（取消 Job 等极少数安全例外单独列白名单），逐路由覆盖；对动态读取配置的动作补并发回归。

#### A-05：更新检查、前端 Releases 与安装器仍指向旧上游仓库

- **位置**：`src/update_check.py:15-17`、`web/frontend/src/runtime/index.ts:8`、`packaging/windows/installer.iss:6-19`、`tests/test_update_check.py:42`。
- **状态**：已确认。当前组合项目发布仓库是 `selinyi123/bil-1`，上述位置仍是 `luovicter-collab/bilibinggo`。
- **影响**：检查更新、打开 Release 或安装器帮助链接可能把用户带到未含 LAS 合并能力的旧项目产物，造成错误安装、回退或数据兼容风险。
- **修复**：建立单一 repository/release URL 常量或构建注入源；更新 API、前端、Inno 和测试期望；新测试断言所有发布入口一致。

### 4.2 P1：强控制流风险，须按外部副作用处理

#### A-06：非幂等 POST 把所有 RequestError 当作可重试，可能重复转发/评论/预约

- **位置**：`src/bilibili_client.py:288-325,334-373`，`post_form` / `post_json`；写调用在 `src/lottery_actions.py:466-541` 和 `src/participation.py:391-434`。
- **状态**：强控制流风险。服务端已处理、客户端在读响应时 `ReadTimeout` / `ReadError` 的场景会被自动重发；同一次调用默认可重试 3 次。
- **影响**：重复转发、评论、收藏或预约切换；第一次转发若响应丢失，exact ownership 台账还可能只记录后一次返回的动态。
- **修复**：非幂等写端默认 `retries=0`；仅对明确幂等接口或具幂等键的请求重试；不确定结果先查询外部状态并记录 `outcome_unknown`。

#### A-07：参与状态探测失败被折叠为“尚未执行”，会 fail-open 并可能误入清理分区

- **位置**：`src/lottery_actions.py:185-235,240-347,371-384,628-652`，`build_dynamic_context`、`is_following`、收藏/转发/评论探测、`follow_user`、`execute_full_participation`。
- **状态**：强控制流风险。探测请求异常/API 失败均返回 `False`；`22014`“已关注”又被当作成功关注，随后只要 `ok=True` 即会移动到临时关注分区。

## 5. 第三方依赖与静态安全检查

### 5.1 前端依赖审计

`npm audit --json` 报告 7 项锁定依赖问题：**1 critical、2 high、4 moderate**。主要根因是开发依赖 `vitest@2.1.9` / 嵌套 Vite/esbuild/PostCSS/nanoid；npm 给出的完整修复路径是 `vitest@4.1.10`，属于 major upgrade。

- critical：Vitest UI server 在受影响版本中可读/执行任意文件的公告；本项目没有把 Vitest UI 作为生产服务启动。
- high：Vite Windows alternate-path 与其他 dev-server 公告，及 nanoid 的极端 DoS 公告。
- 范围判断：这些都是构建/测试依赖；打包后的本机应用没有把 Vite/Vitest 作为运行时 Web 服务发布。源码开发时若启动 Vite dev server，仍应视为开发环境风险。
- 建议：单独创建依赖升级任务，先核对 Vite/Vitest 4 的迁移项和 Playwright/TS 兼容性；不要在本次只读审计中执行 `npm audit fix --force`。

### 5.2 未发现的高危模式

对项目自有代码检索后，未发现不可信输入直达 `eval` / `new Function` / 动态脚本注入 / `shell=True` 的 confirmed 路径。前端主要 `innerHTML` 渲染点对用户/API 文本使用 `escapeHtml`，外链经 `safeUrl` 仅允许 HTTP(S)；这不替代未来代码审查，但当前未构成 confirmed XSS。PyInstaller 和打包脚本使用固定 argv 的 subprocess 调用，未见将未经校验用户文本拼入 shell 命令的路径。
