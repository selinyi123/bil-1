# Codex ↔ GPT 规划循环

## 目的

右侧 GPT 负责跨模块规划和产品取舍，Codex 负责本地证据核对、最小实现、测试和交付。GPT 的等待时间不再与本地执行串行浪费：每轮只在规划完成后进入实现，但实现期间不重复发起同一规划请求。

## 固定循环

### 1. 本地状态包

Codex 先收集最小但完整的状态包：

- 当前本地 commit、工作区差异和版本 SSOT；
- 适用的 `AGENTS.md`、`SPEC.md`、`ACCEPTANCE.md`；
- 上一切片的验收结果和未闭环风险；
- 相关模块的调用链、数据库字段、测试入口；
- 不把 Cookie、Token、代理认证或其他秘密放进 prompt。

### 2. 长规划 prompt

发给 GPT 的 prompt 必须要求：

- 先区分本地事实、文档事实、推断和未知；
- 只选一个下一切片，写明非目标；
- 指定文件、类、函数、调用链和数据边界；
- 写状态机/事务/并发/失败回收/兼容桥；
- 为每个关键不变量指定测试和失败时的停止条件；
- 对 AI comment、`only_followed`、`randomDynamic`、Line registry、per-account 配置给出“做/不做/延后”的证据和代价；
- 最后给出可直接执行的 Codex checklist。

规划过短时不得直接实施；应补发状态、约束和要求的输出结构，直到规划足以支撑一个独立切片。

### 3. 本地实现

规划完成后，Codex：

1. 只实现该切片，不顺手迁移邻近产品功能；
2. 保留已有用户修改和兼容 wrapper；
3. 先写或补不变量测试，再改调用链；
4. 不接触秘密，不做部署、真实登录、真实参与、通知外发或远端写操作；
5. 遇到规划与本地代码冲突时，以本地代码/测试为证据，暂停扩展范围并记录冲突。

### 4. 验证与回传

按风险运行最小充分验证：聚焦测试、必要的全量测试、前端构建、编译和 diff 检查。完成后整理：

- 修改文件和关键调用链；
- 命令、结果和未执行项目；
- 新增不变量测试；
- 仍然存在的风险和下一轮需要 GPT 决策的问题。

下一轮再把这份证据作为状态包发送给 GPT，不让 GPT 重新猜测本地状态。
