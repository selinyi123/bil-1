# 第二部分：过度设计与安全冗余评估

## 2.0 结论摘要

- **点名的两项机制：一项不存在，一项判定为合理设计。**
  - 账号冷却机制：**代码库中不存在**。全仓库 `cooldown|冷却|cool_down` 零命中。
  - 任务模拟机制：存在（`dry_run`），但**不是**第二套执行引擎，判定为**合理**。
- 真正的问题不是「机制太多」，而是三类：
  1. **死机制**——已写好、无人调用、部分一调即崩；
  2. **有名无实的机制**——留了接口和调用点，实现是空的或永不触发；
  3. **未闭环的机制**——一端实现了，另一端从不消费。
- 安全机制方面，**没有发现「为安全而安全」的冗余堆砌**；风险在相反方向：几处安全承诺**强于实际实现**（文档/命名承诺跨进程互斥、承诺熔断，实际做不到）。

## 2.1 用户点名的两项机制

### 账号冷却机制：不存在

```
grep -rniE "cooldown|冷却|cool_down" → 0 命中（.py/.ts/.md 全仓库）
```

现存的节流手段共 4 层，均为**请求级/动作级**，无账号级状态机、无持久化 lifecycle：

| 层 | 位置 | 性质 |
| --- | --- | --- |
| 全局令牌桶 | `src/bilibili_rate_limit.py:55` | 进程内，默认 3 rps |
| 业务码退避 | `src/bilibili_client.py`（-352/-509/-799） | 单请求内重试 |
| 动作间随机间隔 | `src/lottery_actions.py:620-627` | 0.75~2.25s 随机 |
| 数据源/用户间固定延时 | `src/watch_sync.py:130`、`src/participation.py:558` | 常量 sleep |

三方对比报告 3.13 的判断（「三个基准均无正式账号 cooldown FSM」）与 main 一致。**这一项不构成过度设计，因为它根本没被设计。** 如果确实观察到 B 站封控，缺的是这个机制，不是多了它。

### 任务模拟机制（`dry_run`）：合理，非冗余

`dry_run` 共 59 处、8 个 Python 文件，**复用同一套领域函数**，没有 SimulationExecutor/RealExecutor 两套语义：

```
web/actions.py (透传) → src/participation.py → src/lottery_actions.py
  ├─ 允许：读取当前点赞/关注/收藏/转发/评论状态
  ├─ 禁止：任何写请求
  └─ 禁止：写 participation 台账 / 标记已参加
```

判定依据：
- **它有真实用户价值**：`clear_follows` 是破坏性操作（删动态 + 取关），`dry_run=True` 是其**默认值**（`src/clear_follows.py`）。没有预演的清理功能才是危险设计。
- **它不产生第二套状态**：不新增枚举、不新增存储、不新增执行路径。
- **它的成本是真实的但可控**：每个有副作用的 action 必须正确透传布尔值。项目历史上确实出过「中层写死 `dry_run=False`」的贯穿失效（已修复，见 `docs/13-LAS功能迁移审计.md` 第 43 节第 1 条）——这是**实现风险，不是设计冗余**。

对比参照：LAS 用 `NOT_GO_LOTTERY` 一刀切禁止参与，机制更小但无法逐动作预览。bil-1 的选择与其「本地 Web 产品」定位一致。

## 2.2 确证的冗余：死机制（4 处）

### ① `web/enrich_prune.py` —— 死代码 + 一调即崩

```
全仓库调用点：0（仅函数自身定义）
web/enrich_prune.py:39   cache_hits=result.cache_hits,
src/fetch_activity_info.py EnrichResult 字段：无 cache_hits
```

整个模块 45 行，构造 `EnrichResult` 时传入不存在的字段 → 任何调用立即 `TypeError`/`AttributeError`。它同时具备三个特征：无人调用、必然崩溃、审计报告为它写了一条「complete 语义被篡改」的分析。**这是纯负债。**

### ② 详情 API 熔断器 —— 两份拷贝，且永不熔断

```
src/lottery_api.py:31-48        _detail_api_lock / _detail_api_enabled / is_ / disable_ / reset_
src/lottery_classifier.py:24-41 完全独立的同名 flag + lock + 三函数

disable_detail_api() 全仓库调用点：0
```

也就是说：
- 这是一个**被复制了两份**的进程级熔断器；
- 两份互不感知（一份 disable 不影响另一份）；
- **两份都从来没有被 disable 过** —— 熔断器只有 `reset`，没有 `trip`。

`is_detail_api_enabled()` 在 `lottery_api.py:199,253` 与 `lottery_classifier.py:59` 被检查，但恒为 `True`。剩下的只有 `reset_detail_api_state()` 的 4 个调用点，其中 1 个（`fetch_activity_info.py:261`）还是 `NameError`。

**判定**：设计意图（限流时降级跳过 detail API）合理，但当前是一个 0 收益、双份维护、且带一个硬故障的空壳。

### ③ `count_skipped_pending_retry()` —— 恒返回 0，无调用点

`src/fetch_activity_info.py:97`。审计报告已指出「说明技术失败待重试模型尚未真正实现」。它是 P0-1（source checkpoint 前移但失败 link 未入库）**本应对应的补偿机制的空占位**。

### ④ `should_recommend_at_check()` —— 恒返回 False，只被测试引用

```
src/draw_reminder.py:83        丢弃全部参数，return False
tests/test_draw_reminder.py:32,44   assert ... is False
```

生产代码零引用。测试在**断言死代码保持死的状态**——这类测试提供的是虚假覆盖率，不是回归保护。

## 2.3 确证的冗余：未闭环机制（2 处）

### ⑤ `X-Api-Contract` 契约版本 —— 后端全套实现，前端零消费

```
web/api_contract.py   常量 + should_attach_ + attach_×2 + ASGI 中间件 + OpenAPI patch
web/frontend/src/     "X-Api-Contract" / apiContract 命中：0
```

后端为每个 `/api/*` JSON 与 SSE 响应加头、并在 OpenAPI info 里声明 `x-api-contract`，但**没有任何消费者会因版本不匹配而改变行为**。契约代的价值来自「客户端发现不兼容后拒绝/提示」，这一半从未实现。当前它只是一个恒定 header。

### ⑥ `invalidate_activity_cache()` —— no-op，22 个调用点

活动数据已全量走 DB，该函数体为空操作，但 22 处调用点仍在 `web/actions.py` 等处保留。这些调用**读起来像是有缓存一致性语义**，实际什么都不做。它是文件缓存时代的化石，会持续误导维护者判断「这里是否需要失效缓存」。

## 2.4 结构性过度设计：横向协调面

这一类不是死代码，是**同一事实被多处重新表达**。三方对比报告的结论在 main 上依然成立，只是需要换实证：

### ⑦ 身份解析入口 6 个

| 函数 | 位置 | 语义 |
| --- | --- | --- |
| `get_login_uid()` | `src/bilibili_auth.py:32` | 当前 cookies.txt 的 UID |
| `resolve_effective_uid()` | `src/bilibili_auth.py:37` | env > 账号池 active > cookies.txt |
| `pool_active_uid()` | `src/account_pool.py:115` | 账号池 active |
| `get_active_uid()` | `src/account_pool.py:125` | 账号池封装 |
| `get_active_uid()` | `src/user_data.py:14` | **同名不同实现**，委托 bilibili_auth |
| `participation_uid()` / `settings_uid()` | `src/db/uids.py:9,16` | 每次调用重新解析，无 UID 时回落 `__legacy__` / `__global__` |

其中 `src/account_pool.get_active_uid` 与 `src/user_data.get_active_uid` **同名、语义不同**，是最容易误用的一处。维护者要回答「这个写请求用的是谁」，需要同时理解 6 个入口的优先级。

### ⑧ 业务规则在前后端各实现一遍

「参与是否算成功」这条核心规则同时存在于：

```
src/participation_log.py:108,120   _comment_failure_optional / participation_succeeded
web/frontend/src/jobs/index.ts:645,651  commentFailureOptional / participationSucceeded
web/frontend/src/dom.ts:272        COMMENT_OPTIONAL_PATTERNS = [/关注UP主/i, /关注 up/i, /7\s*天/i, /code=12078/i]
```

前端用**正则匹配中文错误文案**复刻后端判定。后端文案一改，前端静默判错。同类问题还有 `web/actions.py:_pipeline_substep_index()`（用中文关键字「入库/详情/分类」推断流水线阶段）和 `web/api_errors.py:_http_exception_to_code()`（靠 detail 文案推断错误码）——**把中文提示文本当成了模块间接口**。

### ⑨ 重试层叠

`src/watch_feed.py:69-95` 外层 `PAGE_RETRY_ATTEMPTS` 循环，内层 `get_json(retries=1)`，客户端自身还有业务码退避。一次逻辑分页可放出数倍实际 HTTP 请求——与「令牌桶限流是为了风控友好」的设计目标方向相反。

### ⑩ 单点使用的抽象：`Line`

`src/line.py` 迁移自 LAS，全仓库唯一调用点是 `src/bilibili_client.py:599` 的 `get_user_followers`。LAS 里 Line 覆盖多个高频接口才划算；这里一个 45 行的类 + 一个调用点，抽象尚未偿还成本。**不算错误，但目前是净成本**——要么扩大使用，要么内联。

## 2.5 安全机制评估

### 判定：没有发现「为安全而安全」的堆砌

逐项核对，每一条都对应真实威胁：

| 机制 | 位置 | 对应的真实威胁 | 判定 |
| --- | --- | --- | --- |
| Host/Origin 本地守卫 | `web/local_guard.py` | 浏览器 DNS rebinding / CSRF 打本地控制面 | **必要**（这是 Web 形态独有威胁，LAS 无此攻击面） |
| 日志/诊断脱敏 | `log_redact.py`(52行) + `secrets_inventory.py`(100) + `diagnostics.py`(127) | Cookie/LLM Key 外泄；LAS 正是在这一项上明文打印 Cookie | **必要** |
| 密钥文件原子写 + 权限收紧 | `secure_files.py` | 多进程写坏 + 同机他用户读取 | **必要** |
| 配置 secret 占位符回填 | `config_files.py` | Web 端保存配置时清空真实凭据 | **必要**（且 `_restore_value` 有 P1-4 缺陷） |
| 清理归属台账 + dry-run 默认 | `clear_follows.py` | 误删用户原创动态 | **必要** |
| DS-10 外部源 URL/路径校验 | `source_settings.py` | `file://` 逃逸出 BINGGO_HOME | **必要** |
| Job 运行中禁写守卫（9 处） | `web/app.py`、`web/product_routes.py` | 切号/改代理与运行中任务竞态 | **必要** |

**没有一项属于「防御性复杂度但无对应威胁」。** 这与三方对比报告 8.6 的判断一致。

### 但有三处「承诺 > 实现」，比冗余更危险

| 问题 | 位置 | 实质 |
| --- | --- | --- |
| **命名/文档承诺跨进程互斥，实际只有进程内 RLock** | `src/user_data_lock.py`；`participation.record_participation_outcome_unlocked` 的文档称调用者持有「跨进程/线程互斥」 | `scripts/participate.py` 是独立 CLI 进程，可与 Web Job 并发写同一 DB。锁的名字让调用者以为安全 |
| **权限检查失败被当作「权限没问题」** | `src/config_health.py:_perms_too_open()`，stat 异常返回 `False` | 「检查不了」和「检查通过」在返回值上不可区分 |
| **Windows 下权限硬化恒为空操作** | `src/secure_files.py:harden_file_permissions()` 直接 `return False` | Windows 是主要分发平台之一，密钥文件实际未收紧；调用方无从得知 |

这三条与审计报告 P1-2「多个 probe 把『未知』压缩为 `False`」是同一个模式：**用布尔返回值表达三态事实**。它不是冗余，是表达力不足。

### 一处需要警惕的生产开关

`web/app.py:727-731`：`BINGGO_E2E=1` 时 `install_e2e_hooks(app)` 会 monkey-patch `account_service.get_account_profile/get_account_extras` 和 `api_errors.is_llm_ready`，并注册 `/api/testing/e2e-state`。

现有防护是恰当的（loopback 校验 + 启动 warning + 环境变量默认不设），**不判定为缺陷**。但这是全仓库唯一一条「打包产物内自带、可用单个环境变量伪造登录态与 LLM 就绪态」的路径，值得在发布检查清单里显式确认。

## 2.6 明确不属于过度设计的部分（避免误伤）

以下常被误认为「虚胖」，但与产品目标等量，不建议削减：

- **SQLite + schema 迁移**：支撑活动库查询/统计/跨重启历史，是 Web 形态的必需品，不是 JSON 的镀金替代。
- **Job 持久化 + SSE**：用户要看到「重启后上次任务发生了什么」，内存 JobStatus 做不到。
- **DS 检查点增量**：`commit_source_checkpoint` 让同一专栏不重爬，是**降低**请求量的机制（虽与 P0-1 组合出状态冲突，但机制本身正确）。
- **WBI 签名 + 令牌桶**：直接对应风控，LAS 恰恰缺这一项。
- **参与前幂等探测**：`build_dynamic_context` 增加读请求，但避免重复关注/评论的副作用，权衡合理。
- **诊断包导出**：本地产品的排障刚需。
